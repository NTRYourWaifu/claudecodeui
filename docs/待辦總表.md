## 0. 這個專案的鐵律（違反會壞掉，每次動工前看一眼）

| 禁止 | 為什麼 |
|---|---|
| **不准跑 `npm install` / `npm update`** | 會覆蓋掉 `node_modules/@anthropic-ai/claude-agent-sdk/sdk.mjs` 的 cross-drive cwd 修補。沖掉之後這台機器上**完全不能對話**（claude.exe spawn ENOENT）。真的必須跑，事後要重跑 `patch-sdk.cjs` / `patch-sdk2.cjs` |
| **不准 `git pull` / `git merge origin/main`** | 上游領先 161 個 commit（我們 v1.32.0 → 上游 v1.37.1）。要抄功能就手動抄單檔，不整批合併 |
| **`.bat` 內容一律純英文** | Windows cmd 用 Big5 解析 UTF-8 中文 → 亂碼被當指令跑 → exit 1，雙擊一閃就死 |
| **Windows 路徑 drive letter 一律大寫** | `process.cwd()` 在 Windows 一律回大寫，canonical path 必須跟著大寫，否則專案清單會分裂成兩筆 |
| **不動認證機制** | 自家帳密 + JWT，單使用者，能用就別碰。忘記密碼救援只有 `reset-password.bat` |
| **改完 Claude 自己跑 `npm run build`** | 使用者不寫程式碼、不手打 npm 指令。他的驗證方式是雙擊 `restart-prod.bat` |

**驗證方式（每項工作完成後）**：
1. Claude 自己跑 `npm run build`（client + server 都要）
2. 請使用者雙擊 `restart-prod.bat`，用手機開 `https://desktop-r37hqa9.tail58509a.ts.net` 看
3. 純視覺的項目（配色、圓角、密度、刻度條）**Claude 驗不了**，一律標 ❌ 未測，等使用者回報

  tail 視窗。log 視窗不是伺服器的 parent，關掉它伺服器照跑（已實測）
- 已實測：launcher 立即返回、pwsh 進程 `HasWindow=False`、3001 被拉起、log 有內容、
  開關 log 視窗後伺服器存活

**決策**：用 PowerShell 7 + WinForms `NotifyIcon` 做常駐托盤，**不做開機自啟**（使用者明確選擇維持手動雙擊）。

**已驗證**：`pwsh -NoProfile -Command "Add-Type -AssemblyName System.Windows.Forms; New-Object System.Windows.Forms.NotifyIcon"` 在這台實測成功回傳物件。零額外依賴，不需要 Electron、不需要 npm 套件。

**契約**：
- 新檔 `F:\Vs\cloudcli\tray.ps1` ＋ 啟動器 `F:\Vs\cloudcli\tray.bat`（純英文）
- 伺服器以**獨立於 log 視窗的行程**啟動 — 關 log 視窗不得中斷伺服器。這是整個需求的核心，不能用「cmd 當 parent」那種寫法

## 10. 捲動被拉走（兩邊都防）

**決策**：使用者不確定觸發情境，所以**兩個嫌疑都防**。

**兩個嫌疑（都在 `F:\Vs\cloudcli\src\components\chat\hooks\useChatSessionState.ts`）**：

**嫌疑 A — 載入舊訊息後的位置還原算歪**（`:367-374`）
往上捲到 `scrollTop < 100` 觸發載入更早訊息，載完用 `scrollTop = top + (newHeight - oldHeight)` 還原。問題是這個差值在 **Markdown / 程式碼區塊 / 圖片還沒渲染完**時算的，高度之後才變 → 位置就歪掉。這最符合使用者描述的「被拉到二三次對話的位置」。

**嫌疑 B — 新訊息進來搶捲動**（`:666-681`）
`if (!isUserScrolledUp) setTimeout(scrollToBottom, 50)`。`isUserScrolledUp` 由 scroll 事件更新，捲動當下若新訊息剛好到，狀態還沒更新完 → 被拉到底。

**契約**：
- A 的修法方向：還原位置要等內容真的穩定（量測時機要對），不是加大 timeout 硬湊
- B 的修法方向：使用者只要有主動捲動意圖就別搶，判定要即時而不是靠 50ms 後補
- **不要動** `searchScrollActiveRef` 那條路徑，那是從搜尋跳轉進來的，行為是對的

⚠️ **無法自行重現**：Claude 沒辦法在沒有真實長對話 + 真實手機捲動的情況下重現。修完只能標 ⚠️ 半驗，等使用者回報還會不會發生。

## 19. 串流中不跟著捲到底（需求 3.2）

**使用者原話**：「我畫面拖到最新最下面 新出的訊息應該要帶動我滑動 讓我看到最新 現在好像沒有」

**已驗證根因（這條最明確）**：
- 自動捲底的副作用在 `useChatSessionState.ts:745-766`，依賴是 `[chatMessages.length, ...]`
- 但串流是**原地更新同一則訊息**：`useSessionStore.ts:521-547` 用固定 id
  `__streaming_<sessionId>` 反覆覆寫同一筆
- → **串流期間 `chatMessages.length` 完全不變 → 副作用一次都不會重跑 → 不捲**
- 回覆越長跑得越出畫面，正好符合使用者描述

**次要根因（會讓問題變永久）**：`userScrolledUpRef`（`:400`）由 scroll 事件以
`isNearBottom()` 50px 門檻更新。一旦內容長出去超過 50px 而沒有自動捲，
**下一次任何捲動事件都會把它設成 true**，之後整場對話都不再自動捲。這是個閂鎖。

**契約**：

## 21. 在 CloudCLI 看 VSCode 的對話時，AskUserQuestion 的答案整個不見（2026-08-19 追加）

**使用者原話**：「新問題 ask沒有other給我自定輸入」

> 是 VSCode 那邊的 SDK 跑的，CloudCLI 只是在讀同一份 jsonl。已整節重寫。

**真因（實際解析 jsonl 驗證，不是推論）**：


`updatedInput: { ...input, answers }`，把答案寫回 input，所以 input 裡有 `answers`。
**只有外部（VSCode／CLI）產生的逐字稿會中招** —— 而那正是使用者的主要用法。

**契約**：
- `AskUserQuestion` 的 result **不要 `hideOnSuccess`**，改成解析 `The user answered:` 那段，

- `The user answered: …` 是 SDK 產生的固定英文前綴，格式為
  `"問題"="答案", "問題"="答案"`。答案本身可能含中文、逗號、引號，
  **解析要能容錯，解析失敗就原樣把整段文字顯示出來**，不要顯示空白
- 使用者選了「Other」自己打的字，在 tool_result 裡跟一般選項長得一樣，不需要特別區分

## 23. 檔案分頁可以切「專案 / 整台電腦」

**使用者原話**：「我想要在右上角按鈕切換聊天中端機檔案的地方檔案的這個按鈕可以切換出專案範圍查看整台電腦」

**使用者確認的兩個選項**：跟專案模式一樣**可寫**；起點是**快速存取 + 磁碟機 + .claude**。

### 23.1 為什麼不能沿用既有端點

| 端點 | 限制在哪 |
|---|---|
| `/api/projects/:projectId/files*` | 每支都檢查 `resolved.startsWith(projectRoot)` |
| `/api/browse-filesystem` | 走 `validateWorkspacePath()`，鎖 `WORKSPACES_ROOT`（預設家目錄，F 碟拿不到） |

新模組：`server/modules/filesystem/filesystem.routes.ts`，掛 `/api/fs`，
一樣在 `server/index.js` 的 `authenticateToken` 後面。

端點：`GET /roots` `GET /list` `GET /file` `GET /content` `PUT /file`
`POST /create` `PUT /rename` `DELETE /` `POST /upload`。

### 23.2 讀與寫的界線刻意不對稱

- **讀完全放行**（`C:\Windows` 也能列）—— 能登入的人本來就能用聊天終端機走到同一個地方
- **寫有擋** —— `validateWritablePath()` 拒絕磁碟機根，以及
  `C:\Windows`、`Program Files`、`Program Files (x86)`、`ProgramData`、
  `System Volume Information`、`$Recycle.Bin`，加上 Unix 的 `/etc /bin /sbin /usr` 等。
  防的是手機上誤觸，不是防使用者。

### 23.3 一定要 lazy 載入

專案模式一次抓 `getFileTree(path, 10, 0, true)` 整棵樹；從 `C:\` 這樣做永遠跑不完。
`src/components/file-tree/hooks/useComputerFileTree.ts` 把樹拆成兩份平坦 state：
`rootNodes`（捷徑＋磁碟機）與 `childrenByPath`（每個開過的目錄一筆），渲染時才組成巢狀。

**這個拆法的理由不是效能，是 refresh**：新增／刪除後 `onRefresh` 會重讀
「所有已展開過的目錄」，使用者不會被打回頂層。

### 23.4 同一套 UI，兩種定址

`useFileTreeOperations` 內部用 `fileApi` memo 分派：專案模式送 projectId，
電腦模式送絕對路徑。右鍵選單、行內重新命名、刪除對話框**完全沒改**。

`CodeEditorFile` 加了 `scope`，`useCodeEditorDocument` 依它選 `api.fs.readFile/saveFile`
—— 不改這裡的話，點開專案外的檔案會拿到 403。

### 23.5 電腦模式下刻意的行為差異

- 工具列的「新檔案／新資料夾」**隱藏**：沒有隱含的根目錄可以建。右鍵選單仍可用
- 拖放上傳**必須放在某個資料夾上**，放空白處會擋掉並提示
- 資料夾下載 ZIP 會先補抓沒展開的層，上限 500 檔（`MAX_ZIP_FILES`）

### 23.6 沒有型別的相依套件

`mime-types` 與 `multer` 專案沒裝 `@types`，JS 檔不檢查所以一直沒事，新模組是 TS 會爆。
⛔ **不要為此裝新依賴**，已加 `server/types/untyped-modules.d.ts` 放最小宣告。

## 24. 側邊欄狀態點：橘＝工作中、綠＝完成未看 — ✅ 已完成 2026-08-20

### 24.1 原本的問題

舊的綠點只有一個條件：`sessionView.isActive = diffInMinutes < 10`。
也就是「最後活動時間在十分鐘內」，跟正在不在跑、看過沒看過都無關。

所以跑到一半跟剛跑完長得一模一樣，看到綠點不知道該不該點進去。

### 24.2 現在的三態

| 狀態 | 標記 |
|---|---|
| 正在跑 | 橘點 `bg-orange-500` ＋ pulse |
| 跑完了，還沒進去看 | 綠點 `bg-green-500`，不會動 |
| 看過了 | 沒有點 |

跟時間完全脫鉤。跑兩小時就橘兩小時，跑完擺三天沒看就綠三天。

### 24.3 「正在跑」的來源是後端，不是本機猜的

後端本來就有 `getActiveClaudeSDKSessions()` 這些現成清單，先前前端完全沒用。

- 即時：`server/modules/websocket/services/websocket-state.service.ts` 新增
  `broadcastToClients` / `broadcastSessionRunState`，
  `claude-sdk.js` 的 `addSession` / `removeSession` 各呼叫一次
- 兜底：前端每 15 秒發一次既有的 `get-active-sessions`

⚠️ **只有 Claude 走即時廣播**。cursor / codex / gemini / grok 的行程登記散在五、六處，
而且中途會用 `processKey` 這種暫時鍵再換成真 sessionId，硬插廣播容易插錯。
那四家靠 15 秒輪詢，最多慢一輪。

因為狀態出自伺服器，**電腦上開跑、手機上也看得到橘點**。

### 24.4 「已看」存在瀏覽器，靠 baseline 擋住舊對話

`src/contexts/SessionActivityContext.tsx`，三個 localStorage 鍵：

| 鍵 | 內容 |
|---|---|
| `session-seen-at` | 每個對話最後被看的時間 |
| `session-finished-at` | 每個對話跑完的時間（前端自己記） |
| `session-seen-baseline` | 第一次啟用這功能的時間 |

**baseline 是必要的**：沒有它，第一次上線時所有舊對話都「從沒看過」，會整排亮綠。
比 baseline 舊的活動一律當作已看。實測 15 個對話只有 1 個亮，就是它在擋。

**finishedMap 也是必要的**：對話清單是背景 watcher 掃 jsonl 掃出來的，
`lastActivity` 會晚於實際跑完的瞬間。前端自己記完成時間，綠點才能立刻亮。
該對話被看過之後這筆就刪掉。

兩個 map 都有 300 筆上限，超過留最新的。

比較時給 5 秒寬容，因為伺服器跟瀏覽器的時鐘不會完全一樣。

### 24.5 開著它跑完就算看過

`AppContent` 把當前開啟的 sessionId 餵給 provider。provider 這樣處理：

- 進入 / 離開某個對話 → 兩邊都標已看
- 開著它的時候跑完 → 直接標已看，不寫 finishedMap
- 開著不動 → 每 10 秒刷一次已看時間

### 24.6 順手清掉的東西

`isActive` 從 view model 跟型別都刪了，`createSessionViewModel` 的 `currentTime`
參數也一起拿掉（沒人用了）。

### 24.7 驗證到哪

免登入測試伺服器（platform 模式綁 127.0.0.1）＋ Playwright，
用一個只在測試腳本裡的控制埠直接呼叫 `broadcastSessionRunState`，
所以走的是**真的 WebSocket 廣播**，不是前端假造的事件。

實測過的六件事：

1. 15 個舊對話只有 1 個亮綠點（baseline 有擋住）
2. 廣播 running=true → 該列變 `animate-pulse bg-orange-500`
3. 廣播 running=false → 變成不會動的綠點，`session-finished-at` 有寫進去
4. 點進該對話 → 點全部消失，`session-seen-at` 寫入、`session-finished-at` 清空
5. 開著 A 對話讓 A 跑完 → 不留綠點
6. 開著 B 對話讓 A 跑完 → A 亮綠點；重整頁面後綠點還在

⚠️ 沒實測：真的跑一輪 Claude 對話（會花額度）、手機實機。

### 24.8 順手發現、沒動的舊 bug

測的時候 console 出現一輪 `WebSocket not connected`：連線其實已經斷了，
但 `isConnected` 還是 true，因為重連只綁 `onclose`、沒有心跳。
這就是記憶裡那條半死連線，不在這次範圍內，沒動。

新加的 15 秒輪詢剛好會踩到它，所以斷線時 console 會多幾行警告。

## 25.3 決策（含否決的方案）

### 隱藏捲軸

`ScrollArea` 加一個 `hideScrollbar` 布林參數，內層 div 才有辦法掛上 `scrollbar-hide`。
只有側邊欄那一顆打開它。

否決：直接在 `index.css` 把全域 `.overflow-y-auto` 隱藏捲軸。
理由是聊天區與程式碼編輯器都靠捲軸判斷位置，一起隱掉會退步。

### 三段展開

新增一個獨立狀態 `fullyExpandedProjectId: string | null`，跟現有的
`expandedProjects` 並存。三段對應：

| 階段 | 條件 | 畫面 |
|---|---|---|
| 0 收起 | 不在 `expandedProjects` | 只有專案列 |
| 1 預覽 | 在 `expandedProjects`，非 `fullyExpandedProjectId` | 3 列全高 + 第 4 列半高 |
| 2 全開 | 等於 `fullyExpandedProjectId` | 固定約 10 列高，內部自捲 |

- 階段 1 → 2：**點那個半高的第 4 列**（使用者已確認）
- 2 → 0、1 → 0：點最上面的專案列
- 切換到別的專案時 `fullyExpandedProjectId` 自動歸 null

否決：把專案列做成三段循環（點三次才收起）。使用者選了半高列觸發，

### 高度怎麼算

**不准寫死像素。** 用 ref 量第一列渲染出來的真實高度 `rowH`，然後：

- 階段 1：`maxHeight = rowH * 3.5 + 列間距 * 3`
- 階段 2：`maxHeight = rowH * 10 + 列間距 * 9`

理由：手機版與電腦版行高不同，寫死一定有一邊錯。量不到時的退路值
（手機 56、電腦 44）是**目測估的，必須實測校正**。

`overscroll-contain` 是「滑到底不要把外層一起帶走」的關鍵字，少了它需求第 3 條就是壞的。
階段 1（3.5 列）也要能內捲，不是只有階段 2。

## 26.2 已驗證的事實（含出處）

### Claude Code 官方定義的行為（文件原文，2026-08-20 抓取）

出處 <https://code.claude.com/docs/en/interactive-mode>「Queue messages while Claude works」

| 情境 | 官方行為 |
|---|---|
| 忙碌時按 Enter | 排隊，**不中斷** 當前這輪；排隊項目列在輸入框**上方** |
| 排隊時 Claude 正在跑工具 | 那批工具一跑完，**同一輪內**就把訊息交給 Claude |
| 這輪結束時仍在隊列 | 當作下一輪送出，**每則各自一則**，不合併 |
| 按 Esc | 中斷這輪，排隊的東西**立刻送出** |
| 從輸入框第一行按 Up | 把排隊項目取回輸入框，一則一行，排在已打的字前面 |

所以「插話」有兩種送達時機，**輪內**與**輪後**，兩種都要做才等於使用者要的那個。

### SDK 能力（`node_modules/@anthropic-ai/claude-agent-sdk` 0.2.116）

- `query({ prompt })` 的 prompt 型別是 `string | AsyncIterable<SDKUserMessage>`（`sdk.d.ts:2078`）
- 傳字串 ＝ single message mode，官方明文**不支援** dynamic message queueing 與 real-time interruption
  （<https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode> 的 Limitations 區塊）
- 傳 async 產生器 ＝ streaming input mode，中途 yield 新訊息就會被吃進當前這輪
- `Query` 另有 `streamInput()`、`interrupt()`、`setModel()`（`sdk.d.ts:2060`、`:1882`、`:1896`），
  註解寫明「only supported when streaming input/output is used」

### CloudCLI 現況（三個阻擋點，全部確認過）

| 位置 | 現況 |
|---|---|
| `server/claude-sdk.js:642` | 每輪 `query({ prompt: finalCommand })`，**傳字串** |
| `server/claude-sdk.js:239` | 用 `sdkOptions.resume = sessionId` 接上一輪；`:719` 收到 result 就 `removeSession` |
| `src/components/chat/hooks/useChatComposerState.ts:546` | `if (!currentInput.trim() \|\| isLoading \|\| !selectedProject) return;` — 忙碌時送出函式直接不做事 |

真正能中止的那顆在 `ClaudeStatus`（`ChatComposer.tsx:190`）。

## 26.3 決策（含否決的方案）

### 分兩階段，兩階段都要做才算完成

**階段一（前端佇列）** — 覆蓋「輪後送達」。忙碌時送出不再被吃掉，訊息進前端佇列，
收到 `complete` 事件後逐則送出。零伺服器改動。

**階段二（後端 streaming input）** — 覆蓋「輪內送達」。把當前這一輪的 query 從
字串 prompt 改成 async 產生器，讓輪進行中推進去的訊息當場被 Claude 讀到。

### 關鍵決策：query 不做常駐，只在該輪存活期間接受插話

產生器的第一則就是原本的 `finalCommand`；收到 `result` 訊息後**結束產生器**，
query 照常自然結束、照常 `removeSession`。

- 輪還在跑 → 訊息推進產生器，走輪內路徑
- 輪已結束 → 後端拒收，前端佇列走原本的「新開 query + resume」路徑

**為什麼不讓 query 常駐**：常駐等於每個開著的對話都掛一支 claude 子行程。
這台是單人多對話，加上記憶裡那條半死連線（連線斷了伺服器不知道），
常駐必然留下殭屍子行程。用完就收，session 生命週期、abort、resume 全部不用動。

### 否決的方案

| 方案 | 為什麼不做 |
|---|---|
| 只做階段一就收工 | 使用者明說要 VSCode 那種，那包含輪內送達。少做一半不算完成 |
| 收到插話就 `interrupt()` 再把兩句合併重送 | 會丟掉 Claude 這輪做到一半的成果。排隊的定義是不中斷 |
| 把佇列裡多則合併成一則送 | 官方是各自一則。合併會讓 Claude 誤判成一段連續指令 |

## ✅ 25.10 使用者回饋後的修正（2026-08-20）

兩點：**預覽階段也要能內捲**、**預覽階段從 3 列改成 5 列**。

### 提示條改成黏在捲動容器底部

25.9 當時把預覽階段設成不可捲，理由是半高列同時是展開按鈕，蓋在上面的按鈕會吃掉拖曳。
現在改法：**提示條搬進捲動容器裡面**，用 `position: sticky; bottom: 0` 釘在底緣。

它變成捲動容器的子孫之後，手指在它上面拖曳走的是瀏覽器原生的捲動，
放開時瀏覽器自己會抑制 click；點一下才觸發展開。絕對定位的浮層做不到這件事。

兩個階段現在都是 `overflow-y-auto overscroll-contain scrollbar-hide`。

### 列數常數

| 常數 | 舊 | 新 | 為什麼 |
|---|---|---|---|
| `PREVIEW_ROWS` | 3 | **5** | 使用者要求 |
| `INITIAL_VISIBLE_SESSIONS` | 5 | **10** | **必須大於 `PREVIEW_ROWS`**。等於的話內容剛好填滿容器，捲不動也不會有半高列 |

預覽階段容器高度＝`5 × 38 + 5 × 4 + 19 = 229px`，實測相符。

### 實測：桌機 17/17、手機 17/17

手機這輪多驗了三件事，**用 CDP 送真的觸控輸入**（`Input.dispatchTouchEvent`），
不是合成 TouchEvent —— 合成事件不會驅動瀏覽器的捲動與點擊抑制，驗了等於沒驗：

| 驗的事 | 結果 |
|---|---|
| 在提示條上拖曳會捲動清單 | `scrollTop` 0 → 45 |
| 在提示條上拖曳不會誤觸展開 | 容器高度 229 → 229，沒變 |
| 真的點一下提示條會展開 | 229 → 416 |

觸控目標的疑慮跟著解掉了：現在拖曳與點擊在提示條上都成立，
就算那 19px 不好按，拖曳也不會被它吃掉。

### 24.9 上線後才發現的兩個顯示 bug（2026-08-20 晚間修掉）

功能邏輯從一開始就是對的——狀態拿得到、id 對得上、廣播也送得到——
但畫面上**完全看不到點**。原因全在 CSS，跟資料流無關。

**一、`<span>` 沒有 `block`，寬高被忽略**

舊的綠點是 `<div>`。我抽成共用元件時改用 `<span>`，
span 預設 `display: inline`，**inline 元素的 width / height 直接被忽略**，
所以點渲染成 `0×0` 的盒子。DOM 裡查得到、類別全對、就是畫不出來。

最近對話那份沒中招，因為它的父層是 flex 容器，flex item 會被 blockify。

修法：類別加 `block`。

**二、`-translate-x-1` 讓點溢出捲動容器，被裁成半圓**

點是 `absolute left-0 -translate-x-1`，往列的左外側跑 4px。
對話清單容器是 `overflow-y-auto`（`SidebarProjectSessions.tsx:221`），
而 CSS 規定 `overflow-y` 一旦不是 visible，`overflow-x` 也不會是 visible，
所以溢出的那半邊被切掉。

舊版能看到是因為當時那層還沒有捲動容器。

修法：拿掉 `-translate-x-1`，讓點完整待在列內。

### 24.10 這兩個 bug 為什麼難抓

**`getComputedStyle` 會騙人**。查的時候它一直回報橘點的背景是
`rgb(34, 197, 94)`（綠），連 CDP 的 `CSS.getComputedStyleForNode` 也這樣回，
但 `CSS.getMatchedStylesForNode` 只列出一條 `.bg-orange-500`（橘），
把同一個節點複製到 `<body>` 底下又變回橘色。

**最後是靠截圖定案的**——畫面上明明就是橘的。
量到的顏色是假象，真正的問題是尺寸和裁切。

⚠️ **教訓：查視覺問題先截圖，不要先信 computed style。**
之前記憶裡寫「驗視覺不要只靠肉眼看截圖，要遍歷 DOM 取 computed style」，
那條在查配色殘留時成立，但**查「東西看不見」時剛好相反**，
computed style 完全無法反映 0×0 和被裁切這兩種情況。

### 24.11 補做的加固：WebSocket 訊息會被覆蓋

查的過程順手發現的真缺陷，跟上面兩個無關但值得記。

`WebSocketContext` 只有一個 `latestMessage` 狀態格。
兩則訊息若落在同一個 React 更新批次，前一則直接被蓋掉，等於沒收到。
對話開跑的通知後面緊接著大量回覆內容，正是最容易被蓋掉的位置。

已加 `subscribe(listener)`，訂閱者收得到每一則訊息。
既有消費者仍走 `latestMessage`，沒動。
